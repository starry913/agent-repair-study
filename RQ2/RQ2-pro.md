# RQ2：Subtask local outcome 如何在修复过程中传递？

给定修复轨迹：

$$
S(T)=\langle s_1,s_2,\dots,s_m\rangle,
\qquad s_i=\langle \tau_i,A_i,o_i\rangle,
\qquad o_i\in\{+,-,?\}
$$

RQ2 分析相邻或连续 subtask 的 local outcome 关系：

$$
P(o_j\mid \tau_i,o_i,\tau_j)
$$

Local outcome 是依据 reference patch 进行的离线评价，并非 agent 运行时收到的反馈。RQ2 不使用最终 resolved 标签。除特别说明外，单元均为 `n / conditional share`。

本节从最新版 Pre-12 的 1,500 条轨迹、21,142 个 subtask records 重新计算全部结果。

---

## RQ2.1：Failure Reproduction 的 local outcome 与后续 Fault Localization 有什么关系？

RQ2.1 使用全部 6,287 个相邻 `FR -> FL` 转移。

| Agent | `FR+ -> FL+` | `FR+ -> FL-` | `FR- -> FL+` | `FR- -> FL-` | `FR? -> FL+` | `FR? -> FL-` |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Total | 2497 / 75.1% | 828 / 24.9% | 1595 / 60.9% | 1023 / 39.1% | 243 / 70.6% | 101 / 29.4% |
| Lingxi | 1886 / 76.8% | 569 / 23.2% | 956 / 73.0% | 354 / 27.0% | 195 / 83.7% | 38 / 16.3% |
| Moatless | 218 / 68.6% | 100 / 31.4% | 398 / 59.7% | 269 / 40.3% | 40 / 58.0% | 29 / 42.0% |
| OpenHands | 393 / 71.2% | 159 / 28.8% | 241 / 37.6% | 400 / 62.4% | 8 / 19.1% | 34 / 81.0% |

### 主分析：为什么 `FR-` 后仍会出现 `FL+`？

我们检查每个 `FR- -> FL+` 之前是否已经出现 `FL+`，并区分当前 `FR` 是否执行了程序。分类不使用后续结果。

| 原因 | Total | Lingxi | Moatless | OpenHands |
| --- | ---: | ---: | ---: | ---: |
| 确认已知正确目标 | 962 / 60.3% | 791 / 82.7% | 133 / 33.4% | 38 / 15.8% |
| 扩展已知正确目标 | 13 / 0.8% | 6 / 0.6% | 3 / 0.8% | 4 / 1.7% |
| 基于静态上下文首次定位 | 503 / 31.5% | 159 / 16.6% | 254 / 63.8% | 90 / 37.3% |
| 执行后首次定位 | 117 / 7.3% | - | 8 / 2.0% | 109 / 45.2% |

**Finding 1：`FR- -> FL+` 主要不是失败复现产生了新的定位线索，而是 agent 在局部复现未对齐后继续使用历史目标或静态上下文。** 其中 60.3% 只是重新确认此前已经找到的正确目标，真正由当前执行之后首次完成定位的仅占 7.3%。这是因为 local outcome 只评价当前连续片段，`FR-` 不会清除 agent 在更早片段中积累的目标和代码上下文。因此，`FR -> FL` 的结果传递具有历史依赖，不能只根据相邻两个标签解释。

### 分分析

1. **复现质量仍会影响紧随其后的定位质量。** `FR+` 后出现 `FL+` 的比例为 75.1%，高于 `FR-` 后的 60.9%，说明与目标 failure 对齐的证据能够收紧后续定位空间，但这种影响不足以覆盖历史上下文。
2. **`?` 不是介于 `+` 与 `-` 之间的中间等级。** `FR? -> FL+` 为 70.6%，反而高于 `FR- -> FL+` 的 60.9%。`?` 表示证据不足，而 `-` 表示已有明确行为但未与 oracle 对齐，二者不能按质量高低排序。
3. **不同 agent 通过不同信息来源跨过 `FR-`。** Lingxi 的 `FR- -> FL+` 主要是确认已知目标（82.7%），Moatless 主要依赖静态上下文首次定位（63.8%），OpenHands 则更常在执行后首次定位（45.2%）。因此，表面的同一转移可以对应不同的上下文利用方式。

## RQ2.2：Fault Localization 的 local outcome 与首次 Patch Construction 有什么关系？

相邻配对会遗漏 `FL` 与首次 `PC` 之间的其他片段，因此本节将 first `PC` 与此前最近一次 `FL` 配对，共得到 1,425 组。

| Agent | `FL+ -> PC+` | `FL+ -> PC-` | `FL- -> PC+` | `FL- -> PC-` |
| --- | ---: | ---: | ---: | ---: |
| Total | 974 / 95.7% | 44 / 4.3% | 326 / 80.1% | 81 / 19.9% |
| Lingxi | 322 / 96.7% | 11 / 3.3% | 138 / 83.1% | 28 / 16.9% |
| Moatless | 315 / 97.5% | 8 / 2.5% | 90 / 72.6% | 34 / 27.4% |
| OpenHands | 337 / 93.1% | 25 / 6.9% | 98 / 83.8% | 19 / 16.2% |

### 主分析：为什么最近一次 `FL-` 后仍能形成 `PC+`？

| 原因 | Total | Lingxi | Moatless | OpenHands |
| --- | ---: | ---: | ---: | ---: |
| 返回更早定位到的正确目标 | 283 / 86.8% | 130 / 94.2% | 65 / 72.2% | 88 / 89.8% |
| 在更早定位基础上扩展修改范围 | 4 / 1.2% | 1 / 0.7% | 2 / 2.2% | 1 / 1.0% |
| 正确目标由其他 subtask 暴露 | 36 / 11.0% | 7 / 5.1% | 23 / 25.6% | 6 / 6.1% |
| 首次编辑时才暴露正确目标 | 3 / 0.9% | - | - | 3 / 3.1% |

最近一次 `FL-` 是否掩盖了更早的 `FL+`，可进一步分层验证：

| 最近 `FL-` 前的历史 | Total | Lingxi | Moatless | OpenHands |
| --- | ---: | ---: | ---: | ---: |
| 存在更早 `FL+` | 337 / 85.2% `PC+` | 152 / 86.2% | 87 / 77.0% | 98 / 90.8% |
| 不存在更早 `FL+` | 70 / 55.7% `PC+` | 14 / 50.0% | 37 / 62.2% | 19 / 47.4% |

**Finding 2：首次 patch 继承的是整段定位历史，而不是最近一次定位结果。** 在 `FL- -> PC+` 中，86.8% 的 patch 返回了更早已经定位到的正确目标，另有 11.0% 的目标已由其他 subtask 暴露；只有 0.9% 到首次编辑时才真正发现目标。当最近一次定位为 `FL-` 时，只要此前存在 `FL+`，形成 `PC+` 的比例仍为 85.2%；没有历史 `FL+` 时则降至 55.7%。原因是定位结果会进入持续上下文，后续一次无效搜索只增加候选或暂时偏离，并不会覆盖已经建立的故障假设。

### 分分析

1. **最近一次定位仍具有增量作用，但不能代表全部定位状态。** 最近 `FL+` 后形成 `PC+` 的比例为 95.7%，高于最近 `FL-` 后的 80.1%；然而二者差距远小于忽略历史时所暗示的“定位失败必然导致错误 patch”。
2. **历史定位比跨阶段偶然发现更重要。** `FL- -> PC+` 中 88.0% 建立在更早 `FL+` 上，而由其他 subtask 暴露目标和首次编辑直接发现目标合计仅为 12.0%。因此，跨片段记忆是该反常转移的主要来源。
3. **Moatless 更依赖非 `FL` 上下文补足目标。** 其 25.6% 的 `FL- -> PC+` 由其他 subtask 暴露正确目标，明显高于 Lingxi 的 5.1% 和 OpenHands 的 6.1%，说明 subtask 边界并不等同于信息边界。

## RQ2.3：Patch Validation 的 local outcome 与 Patch Refinement 有什么关系？

RQ2.3 使用最新版严格 `PR` 边界下的 1,683 个相邻 `PV -> PR` 转移。

| Agent | `PV+ -> PR+` | `PV+ -> PR-` | `PV- -> PR+` | `PV- -> PR-` | `PV- -> PR?` |
| --- | ---: | ---: | ---: | ---: | ---: |
| Total | 271 / 64.5% | 149 / 35.5% | 763 / 61.8% | 466 / 37.7% | 6 / 0.5% |
| Lingxi | 40 / 56.3% | 31 / 43.7% | 171 / 64.5% | 91 / 34.3% | 3 / 1.1% |
| Moatless | 79 / 68.7% | 36 / 31.3% | 138 / 54.3% | 113 / 44.5% | 3 / 1.2% |
| OpenHands | 152 / 65.0% | 82 / 35.0% | 454 / 63.4% | 262 / 36.6% | - |

`PV?` 共 28 次，样本较少，完整结果保存在数据文件中，不用于形成 finding。

### 主分析：为什么 `PV+` 后仍会出现 `PR+`？

`PV+` 表示验证命中了 oracle-relevant 测试或行为，并不表示测试已经通过。我们进一步读取 `PV` 内实际执行反馈，并检查 `PR` 是否扩展产品源码文件。

| `PV+` 内的实际反馈 | `PV+ -> PR+` | 该反馈下 `PR+` 比例 |
| --- | ---: | ---: |
| 仅出现 fail | 118 / 43.5% | 75.6% |
| 同时出现 pass/fail，最后为 fail | 77 / 28.4% | 77.8% |
| 同时出现 pass/fail，最后为 pass | 37 / 13.7% | 40.7% |
| 仅出现 pass | 12 / 4.4% | 54.5% |
| 无明确执行反馈 | 27 / 10.0% | 51.9% |

在 271 个 `PV+ -> PR+` 中，258 个（95.2%）继续修改已有产品源码文件，仅 13 个（4.8%）转向新的产品源码文件。

**Finding 3：`PV+ -> PR+` 主要由“相关验证仍然失败”驱动，而不是 agent 在验证通过后继续修改。** 72.0% 的 `PV+ -> PR+` 最后一个明确反馈仍为 fail；当反馈仅包含 fail 或最后为 fail 时，后续 `PR+` 比例分别达到 75.6% 和 77.8%，而混合反馈最后为 pass 时降至 40.7%。同时，95.2% 的 refinement 留在已有源码文件中。原因是 `PV+` 评价验证对象是否与 oracle 对齐，实际 fail 才提供需要继续修正的运行时信号；相关失败通常暴露当前实现中的遗漏，因此主要触发同一修改范围内的语义补全。

### 分分析

1. **`PV` 的 oracle 对齐程度几乎不决定下一次 refinement 的质量。** `PV+` 和 `PV-` 后形成 `PR+` 的比例分别为 64.5% 和 61.8%，只相差 2.7 个百分点。相比之下，实际反馈最后为 fail 或 pass 时，`PR+` 比例相差 37.1 个百分点（77.8% vs. 40.7%）。对 refinement 而言，运行反馈内容比 `PV` 的离线标签更有解释力。
2. **`PR+` 不保证下一次 `PV` 立即转为 `+`。** 在 `PV+ -> PR+` 后，下一次 `PV+` 为 63.5%；`PV+ -> PR-` 后反而为 66.4%。在 `PV-` 后，相应比例为 24.4% 和 30.2%。相邻验证片段经常执行不同测试，因此下一次 `PV` 评价的是新的验证范围，不能被当作同一状态的单调改善。
3. **后循环同时包含修复状态和验证范围两个变化源。** `PR` 改变 patch，下一次 `PV` 还可能改变测试对象；若不区分二者，仅根据 `PV -> PR -> PV` 的正负序列判断“改善”或“退化”，会把测试范围变化误认为 patch 质量变化。

---

## RQ2 小结

| Finding | 主要证据 | 含义 |
| --- | --- | --- |
| `FR- -> FL+` 主要来自历史目标和静态上下文 | 60.3% 确认已知目标；执行后首次定位仅 7.3% | `FR -> FL` 传递具有历史依赖 |
| First `PC` 继承整段定位历史 | 86.8% 的 `FL- -> PC+` 返回更早正确目标 | 最近一次 `FL` 不能代表完整定位状态 |
| `PV+ -> PR+` 主要由相关验证失败驱动 | 72.0% 最后反馈为 fail；95.2% 留在已有文件 | `PV` 的 oracle 标签与实际反馈承担不同作用 |

总体而言，subtask local outcome 的传递不是只由相邻标签决定的一阶过程。前 patch 阶段保留此前形成的目标与代码上下文，后 patch 阶段则同时受到实际运行反馈和验证范围变化影响。分析局部结果关系时，需要同时保留历史状态、运行反馈和当前验证范围。
