# RQ1：Subtask-level repair process 与最终 resolved 之间有什么关系？

给定一条修复轨迹：

$$
S(T)=\langle s_1,s_2,\dots,s_m\rangle,
\qquad
s_i=\langle \tau_i,A_i,o_i\rangle,
\qquad o_i\in\{+,-,?\}
$$

其中，$\tau_i$ 表示 subtask 类型，$A_i$ 表示该 subtask 内部的 action sequence，$o_i$ 表示 oracle-aligned local outcome。RQ1 分析 subtask 的局部结果、路径组成和循环结构与最终 resolved 的关系，所有结果均为描述性关联，不作因果解释。

本节使用同时包含 `PC` 和 `PV` 的 1,491 条完整修复轨迹，其中 1,079 条最终 resolved，整体 RR 为 0.723。

---

## RQ1.1：不同 subtask 的 local outcome 与最终 resolved 有什么关系？

Local outcome 是轨迹结束后依据 reference patch 进行的离线评价，并非 agent 运行时收到的反馈。同一轨迹可以包含多个同类 subtask，因此本表以 subtask record 为统计单位。单元为 `n / RR`。

| `PU` | `+` | 958 / 0.733 | 417 / 0.746 | 356 / 0.713 | 185 / 0.741 |
| `PU` | `-` | 67 / 0.642 | 7 / 0.714 | 23 / 0.565 | 37 / 0.676 |
| `FR` | `+` | 4074 / 0.740 | 2636 / 0.765 | 541 / 0.704 | 897 / 0.687 |
| `FR` | `-` | 3036 / 0.680 | 1534 / 0.690 | 791 / 0.659 | 711 / 0.681 |

| `FL` | `-` | 1952 / 0.654 | 961 / 0.669 | 398 / 0.621 | 593 / 0.651 |

**Finding 1：子任务质量与最终修复结果呈现清晰的分层关联：首次补丁构造最强，补丁验证其次，补丁优化与问题理解居中，故障定位和失败复现最弱。这一层级取决于子任务对最终修复语义的约束强度，而不是它在流程中的先后位置。** `PC` 正负 local outcome 的 RR 差距达到 0.360，`PV` 为 0.125，`PR` 和 `PU` 分别为 0.093 和 0.091，`FL` 和 `FR` 则只有 0.076 和 0.060；其中 `PC` 的优势在三个 agent 上均保持一致。首次补丁同时确定修改位置、实现逻辑和影响范围，是修复过程第一次对完整解决方案作出语义承诺，因此其质量最能区分最终成败。补丁验证直接检验修复行为，但只能约束本地执行所覆盖的场景，未执行路径和隐藏测试会削弱这种关联。问题理解、失败复现和故障定位只提供问题范围、故障现象或相关位置，同一份正确证据仍可导向多种实现，因而不能充分约束最终 patch。补丁优化虽然直接修改代码，却只出现在已有 patch 需要返修的轨迹中，其效果同时受初始错误和任务难度限制，因此关联弱于首次补丁构造。

## RQ1.2：不同 subtask pathway 与最终 resolved 有什么关系？

`Distinct` 表示一条轨迹中出现的 subtask 类型数。

| Distinct subtask types | Total | Lingxi | Moatless | OpenHands |
| --- | ---: | ---: | ---: | ---: |
| 3 | 5 / 0.800 | - | 2 / 1.000 | 3 / 0.667 |
| 4 | 323 / 0.789 | 57 / 0.772 | 112 / 0.804 | 154 / 0.786 |
| 5 | 821 / 0.732 | 318 / 0.796 | 270 / 0.711 | 233 / 0.670 |
| 6 | 342 / 0.640 | 124 / 0.613 | 111 / 0.631 | 107 / 0.682 |

`Distinct = 3` 仅有 5 条轨迹，不用于形成 finding。在其余轨迹中，`D=4` 的 RR 最高，`D=5` 次之，`D=6` 最低；subtask 类型增加并不自动提高修复率。为了判断这些路径为何出现，我们依据 reference patch 的修改范围将任务分为单文件单点、单文件多点、模块内多文件和跨模块多文件。

| 任务类型 | `D=4` | `D=5` | `D=6` | 重复 `FR -> FL` | 重复 `PV -> PR` |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单文件单点修复 | 24.9% | 55.0% | 19.9% | 79.3% | 16.1% |
| 单文件多点修复 | 19.0% | 57.1% | 23.7% | 81.3% | 25.5% |
| 模块内多文件修复 | 19.2% | 46.2% | 33.3% | 87.2% | 23.1% |
| 跨模块多文件修复 | 11.5% | 53.8% | 33.8% | 88.5% | 29.2% |

`D=6` 表示轨迹在问题理解、失败复现、故障定位、补丁生成和补丁验证之外还进入 `PR`；重复 `FR -> FL` 和重复 `PV -> PR` 分别表示对应转换至少出现两次。

**Finding 2：APR agent 在不同任务上共享“问题理解、失败复现、故障定位、补丁生成、补丁验证”的基本流程；任务范围扩大后，新增过程主要表现为重复定位和补丁生成后的优化，而不是形成更多新的修复阶段。** `D=5` 在四类任务中始终占比最高。由单文件单点扩展到模块内多文件时，`D=6` 由 19.9% 升至 33.3%，重复 `FR -> FL` 由 79.3% 升至 87.2%，说明更大的修改范围同时增加了定位和补丁优化压力。进一步跨越模块后，`D=6` 和重复 `FR -> FL` 基本稳定在 33.8% 和 88.5%，但重复 `PV -> PR` 升至 29.2%，表明额外工作开始集中到 patch 形成后的反复修改。结合 `D=4 / 5 / 6` 的 RR 依次为 0.789、0.732 和 0.640，新增 subtask 更适合作为修复困难的过程信号，而不能被解释为更完整或更优的流程。

## RQ1.3：repair loop 与最终 resolved 有什么关系？

路径中存在两类高频循环：patch 前的 `FR -> FL` 与 patch 后的 `PV -> PR`。前者反复收集 failure evidence 并定位 fault target，后者依据 validation feedback 重新修改已有 patch。两类循环发生在不同修复阶段，需要分别分析。

### Patch 前：`FR -> FL` 循环

我们依据 reference patch 判断轨迹第几轮首次到达 fault-relevant source target。`Total` 单元为 `n / RR`，其余单元为 `n / 组内占比 / RR`；零轮轨迹不存在可供判断的 `FR -> FL` 循环。

| `FR -> FL` 循环次数 | Total | 第一轮首次到达 | 第二轮首次到达 | 第三轮及以后首次到达 | 始终未到达 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0 | 67 / 0.776 | - | - | - | - |
| 1 | 215 / 0.800 | 195 / 90.7% / 0.810 | - | - | 20 / 9.3% / 0.700 |
| 2 | 334 / 0.719 | 149 / 44.6% / 0.671 | 173 / 51.8% / 0.780 | - | 12 / 3.6% / 0.417 |
| 3-4 | 351 / 0.661 | 65 / 18.5% / 0.677 | 231 / 65.8% / 0.688 | 32 / 9.1% / 0.562 | 23 / 6.6% / 0.478 |
| 5+ | 524 / 0.731 | 448 / 85.5% / 0.763 | 37 / 7.1% / 0.676 | 24 / 4.6% / 0.542 | 15 / 2.9% / 0.200 |

零轮到一轮的 RR 仅由 0.776 升至 0.800，差异不显著（双侧比例检验，`p=0.673`）；一轮以后 RR 开始下降。

| 循环位置 | n | 扩展任意新候选 | 新增有效目标 | 确认已有有效目标 | 无有效定位增量 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 第 1 轮 | 1424 | 91.2% | 60.2% | 0.0% | 39.8% |
| 第 2 轮 | 1209 | 70.4% | 37.9% | 40.6% | 21.5% |
| 第 3 轮 | 875 | 38.1% | 6.1% | 65.3% | 28.7% |
| 第 4-5 轮 | 1161 | 25.3% | 1.8% | 72.7% | 25.5% |
| 第 6 轮及以后 | 1573 | 8.3% | 0.4% | 64.0% | 35.6% |

**Finding 3：失败复现与故障定位的有效窗口集中在前两轮：第一轮用于直接定位，第二轮用于补救延迟定位；第三轮以后，循环由发现新故障位置转为确认已有目标或无效定位，新增定位收益基本耗尽。** 一轮轨迹中，90.7% 在第一轮到达有效目标；两轮轨迹中，51.8% 依靠第二轮完成首次有效定位，RR 仍为 0.780。到第三轮，新增有效目标的概率由前两轮的 60.2% 和 37.9% 降至 6.1%，第三轮以后才首次到达目标的 RR 也降至 0.542-0.562。与此同时，第三轮确认已有有效目标和无有效定位增量的比例分别升至 65.3% 和 28.7%；第四轮以后，两者合计始终超过 95%。5+ 轮轨迹的 RR 回升不表示长循环有益：其中 85.5% 早在第一轮就已到达有效目标，后续循环主要用于确认已有位置；第六轮以后新增有效目标的概率仅为 0.4%。因此，循环是否应停止，应由边际定位产出而不是累计轮数决定。

## RQ1 小结

| Finding | Evidence | Implication |
| --- | --- | --- |
| 子任务质量与最终结果的关联由其对修复语义的约束强度决定 | `PC > PV > PR ≈ PU > FL > FR`，正负 RR 差距依次为 0.360、0.125、0.093、0.091、0.076 和 0.060 | 改进应优先保证首次补丁同时落实正确位置、逻辑和修改范围 |
| 基本修复流程跨任务稳定，复杂性主要增加循环 | `D=5` 始终最多；任务范围扩大时 `D=6`、`FR -> FL` 和 `PV -> PR` 增加 | 不应将更多 subtask 类型直接解释为更完整或更优的流程 |
| 前循环只有两轮有效定位窗口 | 第三轮新增有效目标降至 6.1%，第六轮以后仅 0.4% | 应根据边际定位产出停止循环 |
| 后循环的价值取决于首次 patch 的修复方向 | `PC-` 可被少量方向性修改救回；`PC+` 随循环增加持续下降 | 补丁优化应根据首次 patch 状态与修改方式进行门控 |

总体而言，成功修复并不依赖更长或阶段更多的路径，而依赖于在前两轮形成有效定位、首次 patch 进入正确方向，并在验证后只进行能够改变错误方向或补齐遗漏的有限优化。
