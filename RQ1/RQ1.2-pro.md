# RQ1.2 Pro：不同 subtask pathway 为什么会对应不同的修复结果？

`Distinct` 表示轨迹中出现的 subtask 类型数。为解释 pathway 差异，本文仅依据 reference patch 的修复拓扑划分任务：一个 source file、一个 hunk 为单文件单点；一个 source file、多个 hunks 为单文件多点；多个 source files 位于同一目录为模块内多文件；跨目录为跨模块多文件。该划分不使用 agent 行为或 resolved 标签。

## 1. `Distinct = 4/5/6` 分别增加了什么？


| Distinct | 高频结构                                                   | 主要增量 | 对应修复压力                                       |
| -------- | ------------------------------------------------------ | ---- | -------------------------------------------- |
| `D=4`    | `(FR -> FL)^k -> FR -> PC -> PV`                       | -    | failure evidence 与 fault target 足以直接形成 patch |
| `D=5`    | `PU -> (FR -> FL)^k -> FR -> PC -> PV`                 | `PU` | patch 前需要显式整理问题约束                            |
| `D=6`    | `PU -> (FR -> FL)^k -> FR -> PC -> (PV -> PR)^r -> PV` | `PR` | 首次 patch 未覆盖完整修复义务，需要验证后补救                   |



| 任务类型     | `D=4` | `D=5` | `D=6` | 首次 patch 覆盖全部 reference source files | 进入 `PR` |
| -------- | ----- | ----- | ----- | ------------------------------------ | ------- |
| 单文件单点修复  | 24.9% | 55.0% | 19.9% | 91.7%                                | 30.7%   |
| 单文件多点修复  | 19.0% | 57.1% | 23.7% | 93.5%                                | 42.0%   |
| 模块内多文件修复 | 19.2% | 46.2% | 33.3% | 25.6%                                | 44.9%   |
| 跨模块多文件修复 | 11.5% | 53.8% | 33.8% | 9.2%                                 | 53.1%   |


**Finding 1：修复位置越分散，agent 越难通过一次定位和修改完成修复。** 单文件任务主要停留在 `D=4/5`，多文件任务更多进入包含 `PR` 的 `D=6`；当修复进一步跨越模块时，新增复杂度不再表现为更多 subtask 类型，而表现为已有 subtask 的反复执行。

## 2. `FR -> FL` 的适配窗口：不同任务应该找多久？



### 表 A：任务类型 × 前循环次数 × RR


| 任务类型     | `0-1`       | `2-3`       | `4-5`       | `6+`        | 更合适的窗口        |
| -------- | ----------- | ----------- | ----------- | ----------- | ------------- |
| 单文件单点修复  | 174 / 0.908 | 310 / 0.800 | 108 / 0.796 | 248 / 0.806 | `0-1`，命中后停止   |
| 单文件多点修复  | 83 / 0.711  | 176 / 0.642 | 52 / 0.654  | 132 / 0.720 | 以目标增益为停止条件    |
| 模块内多文件修复 | 10 / 0.400  | 32 / 0.375  | 12 / 0.417  | 24 / 0.458  | 以目标增益为停止条件    |
| 跨模块多文件修复 | 15 / 0.200  | 54 / 0.500  | 21 / 0.381  | 40 / 0.400  | `2-3`，之后按增益停止 |


表 A 报告 `n / RR`。由于三个 agent 的默认循环粒度不同，原始 RR 只用于描述；循环效应进一步通过同一 instance 上不同 agent 的配对比较估计。

### 表 B：前循环产生了什么？

单元为 `机制占比（关联轨迹 RR）`。机制占比以 `FR -> FL` 对为分母；RR 以至少出现一次该机制的轨迹为分母。


| 任务类型     | 首次锁定正确文件     | 补充遗漏文件      | 确认已有文件       | 无正确文件增益      | 窗口原因                                   |
| -------- | ------------ | ----------- | ------------ | ------------ | -------------------------------------- |
| 单文件单点修复  | 22.1%（0.834） | 0.0%（-）     | 46.2%（0.824） | 31.8%（0.790） | reference 仅有一个文件；首次命中后继续循环不可能补出第二个正确文件 |
| 单文件多点修复  | 21.2%（0.693） | 0.0%（-）     | 47.7%（0.656） | 31.1%（0.679） | 压力来自同一文件内的多个修改点，文件搜索无法替代文件内语义分析        |
| 模块内多文件修复 | 20.7%（0.408） | 3.0%（0.273） | 51.6%（0.420） | 24.7%（0.400） | 循环主要用于确认模块内关联位置，补充正确文件较少               |
| 跨模块多文件修复 | 21.7%（0.441） | 5.5%（0.519） | 42.9%（0.444） | 29.8%（0.407） | 额外循环能够发现遗漏模块，但收益集中在前几轮                 |


**Finding 2：前循环的作用不是“多定位几次”，而是避免在跨模块任务上过早形成 patch。** 在同一 instance 的配对比较中，跨模块任务的 `2-3` 次循环相对 `0-1` 次提高 RR `0.231`，但 `4-5` 次相对 `2-3` 次的差值为 `0.000`。表 B 给出机制解释：只有多文件任务可能补充新的 reference file，且跨模块任务中“补充遗漏文件”的关联 RR 为 0.519，高于“无正确文件增益”的 0.407。相反，单文件任务不存在第二个 reference file；其长循环只能确认旧文件或探索非 reference 范围。因此，前循环的停止条件应是 **是否仍在获得新的正确文件范围**：单文件任务命中后转入文件内分析，跨模块任务允许 `2-3` 次定位，之后只有出现新文件时才继续。

## 3. `PV -> PR` 的指导性：什么时候应该补救，什么时候应该停？



### 表 C：任务类型 × 后循环次数 × RR


| 任务类型     | `0`         | `1`         | `2`        | `3+`       | 更合适的窗口        |
| -------- | ----------- | ----------- | ---------- | ---------- | ------------- |
| 单文件单点修复  | 584 / 0.866 | 121 / 0.826 | 48 / 0.812 | 87 / 0.540 | `0-2`，避免 `3+` |
| 单文件多点修复  | 259 / 0.745 | 71 / 0.648  | 34 / 0.618 | 79 / 0.519 | `0-2`，避免 `3+` |
| 模块内多文件修复 | 45 / 0.467  | 15 / 0.400  | 7 / 0.143  | 11 / 0.364 | `0-1`         |
| 跨模块多文件修复 | 61 / 0.361  | 31 / 0.419  | 11 / 0.455 | 27 / 0.519 | `3+`，但须产生范围增益 |




### 表 D：后循环产生了什么？

单元为 `机制占比（关联轨迹 RR）`。首次/重复由该轨迹中的 loop index 判定；扩展正确范围表示 `PR` 新增此前未触及的 reference source file。


| 任务类型     | 首次扩展正确范围    | 首次同范围补救      | 重复扩展正确范围    | 重复同范围修改      | 窗口原因                             |
| -------- | ----------- | ------------ | ----------- | ------------ | -------------------------------- |
| 单文件单点修复  | 0.9%（1.000） | 33.6%（0.719） | 0.3%（0.500） | 65.1%（0.634） | 重复循环几乎不能增加正确范围，主要是在同一位置反复修改      |
| 单文件多点修复  | 0.5%（0.667） | 28.3%（0.586） | 0.2%（1.000） | 71.0%（0.549） | 补救应完成于同一文件内；多轮重开很少发现新的修复义务       |
| 模块内多文件修复 | 9.6%（0.500） | 30.1%（0.280） | 0.0%（-）     | 60.2%（0.278） | 正确范围扩展主要发生在第一次补救，之后继续循环没有范围收益    |
| 跨模块多文件修复 | 4.1%（0.444） | 27.1%（0.467） | 4.5%（0.556） | 64.3%（0.500） | 唯一仍能在重复循环中持续补充 reference 文件的任务类型 |


**Finding 3：post-patch loop 存在方向相反的任务效应，任务难度不能解释这一差异。** 对同一 instance 进行跨 agent 配对后，`3+` 次后循环相对 `0` 次使单文件单点任务 RR 下降 `0.100`，却使跨模块任务提高 `0.346`，其 95% bootstrap CI 为 `[0.115, 0.615]`。表 D 解释了这一交互：单文件任务的重复循环几乎全部是同范围修改；跨模块任务虽然也以同范围修改为主，但它是唯一在重复循环中仍有可观正确范围扩展的类型，且该机制关联 RR 最高（0.556）。因此，不能设置统一的 loop cap：单文件任务应在两轮内收敛；跨模块任务可以继续，但每一轮都必须证明新增了尚未覆盖的正确范围，否则应停止。
